# Maigret Provider Integration Research for Zima

## API Surface Appendix

Maigret is a local OSINT tool (Python package + CLI) that checks whether a username is present on many sites, and can optionally extract profile attributes and linked identifiers from found profiles. It is explicitly described as “collects a dossier … by username only … No API keys are required”, is a fork of Sherlock, and “currently supports more than 3000 sites”, with the default scan scope being the “500 popular sites … by default.” 

This appendix focuses only on integration-relevant methods/artifacts for the target modules: `username_exposure`, `account_inventory`.

### Artifact: CLI search mode (`maigret USERNAME...`)

**Purpose**: Run username presence checks across sites in the configured database; optionally parse profile pages to extract additional fields and linked identifiers; optionally generate reports (including JSON). 

**Supported entity_type(s)**: Primarily `username` for Zima; Maigret also supports several other identifier types via `--id-type`, but those are out of scope for this provider mapping because Zima’s target entity is username. 

**Auth / execution requirements**: No provider API key; execution requires local runtime (Python/CLI) and network egress to target sites. 

**Key CLI options for Zima integration (documented + code-confirmed)**

- Scope controls:
    - `--top-sites N` (default top 500) and `--all-sites` (`-a`) to scan all sites. 
    - `--tags` filters by site tags (category + country codes), with a warning that tags are “not stable now.” 
    - `--site` restricts to specified site(s). 
    - Mirror inclusion behaviour when using `--top-sites` is explicitly documented (top-N plus “mirror” sites whose `source` points to a parent that appears in the Alexa top-N when disabled entries are considered). 
- Reliability controls:
    - `--use-disabled-sites` is explicitly warned as “may cause many false positives.” 
    - `--self-check` performs a self-check and can disable non-working sites; documentation notes it asks whether to save updates and can rewrite the local DB. 
- Performance controls / rate-pressure controls:
    - `--max-connections` limits concurrent connections (default differs by settings; docs illustrate default 100). 
    - `--timeout` sets per-request wait time; documentation warns higher timeouts can slow scans substantially. 
    - `--retries` retries temporarily failed requests. 
    - No CLI flag for explicit inter-batch “pause/delay” exists in the current upstream CLI implementation (`--pause`/“pause” not present). 
- Determinism controls (critical for Zima module boundaries):
    - `--no-recursion` disables recursive search using additional usernames/IDs found in pages. 
    - `--no-extracting` disables parsing pages for additional data and other usernames. 
- Report selection for integration:
    - `--json TYPE` where `TYPE ∈ {simple, ndjson}`, one report per username. 
    - `--folderoutput PATH` controls the output directory for reports. 
- Database pinning:
    - `--db` can load the Maigret DB from a JSON file or online JSON resource. 

**Common execution outcomes (CLI-level)**

- Successful run with findings: CLI prints found accounts; if `--json` is specified, a JSON report file is written. 
- Successful run with no findings: CLI completes; JSON “simple” report will serialize to an empty JSON object `{}` because the JSON report generator only adds claimed results. 
- Partial/limited run: results may be incomplete by design when scanning only `--top-sites` (default) or filtering by `--tags`/`--site`. 
- Common error pressures: target sites can return blocks/captchas/censorship pages; Maigret can detect some and can print errors with `--print-errors`. 

### Artifact: JSON report file (`--json simple` and `--json ndjson`)

**Purpose**: Machine-readable output for downstream parsing; intended integration path for Zima. Supported report formats include JSON, and CLI supports `simple` and `ndjson`. 

**Execution requirements**: Generated by CLI when `--json` is set; written to disk (per-username). The CLI constructs the filename suffix as `_{args.json}.json` and calls the JSON report saver. 

**Top-level shapes**

- `simple`: One JSON object, where each key is the site name (`sitename`), and the value is a per-site result object (`data`). 
- `ndjson`: Newline-delimited JSON; each line is a per-site result object; Maigret adds a `sitename` field to each record. 

**Inclusion semantics (very important for Zima triggers)**
The JSON report generator explicitly **skips** sites unless:

- the per-site result exists and includes a `status`, and
- `site_result["status"].status == MaigretCheckStatus.CLAIMED`. 

This means: **JSON reports contain only “claimed / username detected” results**, not “available / not detected”, not “unknown / error”, and not “illegal”. 

**Per-site result object: top-level fields (observed from report generation + search result structure)**
The JSON report writes `data = dict(site_result)` and then transforms a few fields:

- `data["status"]` becomes `data["status"].json()` (a dict, not a string / enum object). 
- `data["site"]` becomes `data["site"].json` (site metadata dict in camelCase). 
- `future` and `checker` keys are removed if present. 

From the upstream checking implementation, the site result wrapper includes (at least) these keys before report-time filtering/transform:

- `site` (site object), `username` (string), `parsing_enabled` (bool), `url_main` (string), `url_user` (string), `http_status` (int), `is_similar` (bool), `rank` (int). 
    It may also contain extraction-related keys such as `ids_usernames` / `ids_links` when parsing is enabled, because other parts of Maigret read them from the results structure. 

**Nested object: `status` (dict)** `status` is produced by `MaigretCheckResult.json()` and contains:

- `username`: string
- `site_name`: string
- `url`: string (the user profile URL template resolved for the target site/result)
- `status`: string (e.g., “Claimed”, “Available”, “Unknown”, “Illegal”)
- `ids`: object/dict (extracted IDs/attributes, or `{}`)
- `tags`: list of strings (site tags) 

**Nested object: `site` (dict in camelCase)** `site` is produced by `MaigretSite.json` which:

- converts internal snake_case attributes to camelCase keys,
- removes empty/default values (including `False`, empty strings/lists/dicts, `None`, “username”, and `sys.maxsize`),
- omits internal/non-serializable fields listed in `NOT_SERIALIZABLE_FIELDS`. 

Fields that may appear (conditional on being present/non-default for that specific site record) include:

- `urlMain`, `urlSubpath`, `url`, `urlProbe`
- `disabled`, `similarSearch`, `ignore403`
- `tags` (category/country)
- `type` (identifier type)
- `headers`, `errors`, `activation`
- `regexCheck`
- `checkType`, `requestHeadOnly`, `getParams`
- `presenceStrs`, `absenceStrs`
- `engine`, `engineData`
- `alexaRank`, `source`, `protocol` 

**Status / enum values**

- `MaigretCheckStatus` enum values and meanings:
    - `CLAIMED = "Claimed"` (username detected)
    - `AVAILABLE = "Available"` (username not detected)
    - `UNKNOWN = "Unknown"` (error occurred while trying to detect)
    - `ILLEGAL = "Illegal"` (username not allowable for this site) 
- Site `checkType` values in `data.json` / site metadata (detection mechanism):
    - `message` (most reliable; uses `presenceStrs`/`absenceStrs` in HTML response)
    - `status_code` (2XX means claimed)
    - `response_url` (no redirect + 2XX) 

**Important behavioural nuance for false positives** In the checker implementation, if a site uses `checkType == "message"` and `presenceStrs` is empty, Maigret treats presence as true “for any page” (debug-logged). This is a structural source of potential false positives if absence detection is insufficient. 

### Artifact: Site database (`resources/data.json` plus generated `sites.md`)

**Purpose**: Defines supported sites and their detection logic; central source for site tags, `checkType`, `presenceStrs`/`absenceStrs`, `urlProbe`, `disabled`, etc. 

**Where it lives / how to reference**

- Human-readable list is generated into `sites.md` from the main JSON DB. 
- Machine-readable DB is `data.json` in `resources/`. 

**`urlProbe` semantics (highly relevant to evidence and remediation)**

- `urlProbe` in `data.json` allows Maigret to check existence via an API/JSON endpoint while keeping `url`/`url_user` as the human-readable profile URL. Placeholders: `{username}`, `{urlMain}`, `{urlSubpath}`. 

**Reliability-related fields in DB / site metadata**

- `disabled`: if true, Maigret will skip the check unless forced; CLI warns `--use-disabled-sites` can cause many false positives. 
- `similarSearch`: if true, “a positive result indicates accounts with similar usernames rather than exact matches.” (This should be treated as lower-confidence for Zima inventory.) 
- `checkType`: `message` is documented as “most reliable”. 

### Artifact: Python library interface (`maigret` package, async search)

**Purpose**: Direct integration without the CLI; provides full result objects (including not-found/error) rather than the JSON report’s “claimed-only” subset.

- The “main search func” returns a dictionary keyed by site name, where values include:
    - `url_main`, `url_user`, `status`, `http_status`, `response_text` (may be `None` on error) 
- Maigret’s docs explicitly call out a “Simple API” via the Python package. 

For Zima, this interface is relevant as an **optional** upgrade path if you need:

- negative evidence (not found),
- per-site error classes,
- full coverage stats (found vs error vs not found).

However, your stated integration path is `--json`; so treat Python API as a fallback/advanced path rather than the primary path.

## Signal Contract Table

Maigret’s upstream outputs are best treated as **account discovery/inventory utilities** rather than security findings. The JSON report is “claimed-only” presence evidence and does not, by itself, meet Zima’s severity guide thresholds for breach/stealer/malware/C2/etc. 

Accordingly, **no standalone Zima signals are recommended for this provider at P1**, for either target module. If Zima later introduces an “inventory delta” signal type family (e.g., “new external account discovered”), that would be a product decision not grounded in Maigret’s schema/semantics.

## Severity Rules and Confidence Guidance

Because no standalone signals are emitted, there are no severity rules to codify in `modules/*/rules.py` for this provider. The correct use is to persist Maigret outputs as **inventory/enrichment records** and let other modules (breach, stealer logs, phishing, etc.) drive severity.

## Implementation Notes and Provider Summary

### Mapper and parsing notes for `modules/*/mapper.py`

- Prefer `--json ndjson` for large runs because it can be streamed line-by-line and avoids holding one huge JSON object in memory. (`ndjson` is an officially supported report type and is generated by writing one JSON record per claimed site plus `sitename`.) 
- **Null / empty behaviour**:
    - JSON export is **claimed-only**; so “no accounts found” looks like:
        - `simple`: `{}` (empty object)
        - `ndjson`: empty file (no lines)
            This is a correct “no-hit” state, not an error. 
- **Field paths that must survive parsing (recommended evidence payload shape)**:
    - Top-level: `sitename` (ndjson only), `username`, `url_main`, `url_user`, `http_status`, `rank`, `is_similar`, `parsing_enabled` 
    - `status.*`: `status.username`, `status.site_name`, `status.url`, `status.status`, `status.ids`, `status.tags` 
    - `site.*` (camelCase; conditional): keep the entire `site` dict rather than cherry-picking, because Maigret’s site schema is DB-driven and only non-default keys are emitted. 
- **Defaulting logic (important)**:
    - `site.disabled` and `site.similarSearch` may be missing from JSON because Maigret strips false/default values in `site.json`. Treat missing as false in your mapper. 
- **Reliability filters (implementation guidance; build as configurable, not hard-coded)**:
    - Exclude records where `is_similar == true` (or where `site.similarSearch == true` if present) for “strict inventory” mode. 
    - Consider favouring/allowlisting sites where `site.checkType == "message"` because it is documented as most reliable. 
    - Do not use `--use-disabled-sites` in production default runs; it is explicitly warned to cause many false positives. 
- **Deduplication keys (inventory layer, not signals)**:
    - Recommended natural keys: `(input_username, sitename)` and/or `(input_username, url_user)`.
    - Store `site.urlMain`/`url_main` as a stable grouping field for remediation/delta UI. 

### Provider cautions for the Zima client layer

- **Scope control is mandatory**: default scans are top-500 by popularity; `--top-sites`, `--all-sites`, `--tags`, and mirror behaviour all affect coverage. Treat these as part of the provider configuration that must be pinned per environment. 
- **Database/version pinning**:
    - Maigret can load DB from a file or URL (`--db`), and settings files can override defaults; Maigret settings search order includes package resource settings, user home settings, and local working directory settings. Zima should run with an explicit config/DB path to avoid environment drift. 
- **Interactive modes**:
    - `--self-check` / `--submit` can prompt and rewrite local DB; avoid in headless production runs unless you control TTY interactions. 
- **Legal/ToS considerations**:
    - The upstream project includes a legal-use disclaimer and highlights regulatory responsibility (e.g., GDPR/CCPA). Ensure Zima’s use aligns with your customers’ authorisation model and data handling policies. 
- **Licensing**:
    - Maigret is MIT-licensed. 

### Provider Summary

- Strongest “signal types” (in Zima terms): none. The strongest **inputs** Maigret provides are (a) a broad inventory of sites where the username is claimed, and (b) optional extracted profile attributes/linked identifiers in `status.ids` (enrichment). 
- What Maigret should not be used for:
    - It should not be treated as proof of account ownership/identity; its core function is account/username presence checks as defined by site detection rules (`checkType`, presence/absence strings, etc.). 
    - It should not drive breach/credential-compromise severities; it does not provide breach/stealer/malware semantics. 
- API/auth/rate-limit/licensing cautions:
    - No API keys; rate-pressure is primarily controlled via `--max-connections`, `--timeout`, and `--retries`, not explicit “pause” flags. 
    - MIT licensing: compatible for integration; still review obligations and bundled dependency licences. 
- Recommended Zima treatment at current stage:
    - Treat as **utility_only** for `account_inventory`, and **enrichment_only** for `username_exposure`. Do not emit standalone signals from Maigret at P1; store results as inventory/enrichment and let higher-fidelity compromise modules drive alerting.
